# IPCM 颜色模型与全库拟合审计

本轮完成20款源 LUT 的统一离线拟合和对照。共同算法选中5款新候选，15款保留基线；NC 的暗部偏色没有解决。当前 CCM → 共享 Tone → YCC 模型不足以作为全库高一致性预览的默认方案。后续按原厂 SmartFilter 帧处理链调查完整三维预览，原生参数拟合保留为轻量候选。

## 按影响排序的发现

| 顺序 | 发现 | 证据与处理 |
|---|---|---|
| 1 | 原生颜色域和像素算子顺序尚未标定，原代理直接在显示码值域应用 CCM | 新模型显式区分码值、sRGB线性和原厂静态Gamma结点三种假设；不根据拟合分数选择“真实硬件顺序” |
| 2 | 全局均值会掩盖暗部冷暖做反的问题 | 新增灰阶有符号 R−G、B−G 目标，报告阴影／中间调／高光的方向错误比例 |
| 3 | 原代理省略了Q12配置与原厂矩阵组合时的原生参数舍入及整组越界回退 | 新旧配置统一通过原生参数参考模型评估；与现有C实现逐项对照 |
| 4 | Python浮点强度混合可能把精确半整数移到半点以下 | 整数百分比改用整数分子和 ties-away 舍入。例如54%、Tone索引240、目标15，C结果119，旧Python可能118 |
| 5 | 矩阵、共享曲线之间存在亮度／色度补偿取舍 | 分阶段求解、矩阵正则、曲线单调和平滑约束；独立样本比较量化后的候选 |
| 6 | 拟合模型尚未覆盖全部原生模块 | 发现独立YLUT节点；PCSE已有参数通路，但缺少机身像素响应。二者不能以猜测公式代替真实响应 |

第1项是影响很大的未验证假设，第4项是已复现的实现错误。NC并非由这个小幅舍入错误造成。

## 已核实的数学与原厂接口

现有 RAM 代码以 `profile_Q12 × fresh_stock_matrix` 左乘本轮原厂矩阵，每项除4096并四舍五入，最终原生系数要求−1024…1023；一项越界则整组透传。这个结论描述参数组合代码，尚不证明硬件对像素采用相同的行列方向。

Tone组合为 `creative_T[fresh_stock_Tone[i]]`，代码没有再次生成一张基础sRGB Gamma。原厂 `ipcm_tone_lut` 接收一根指针，复制2048个uint8；已检查接口没有独立RGB曲线选择参数。

原厂默认RGB→YCC矩阵来自IQ静态表：

```text
[ 77, 150,  29
 -43, -85, 128
 128,-107, -21 ] / 256
```

软件参考模型采用单位Q8原厂CCM和上述YCC基底。实际动态CCM、Gamma、非单位CHM、色度中心、量程、像素裁剪和定点运算仍需机身数据确认。原厂参数调用先后不能直接证明硬件像素先后顺序。

新增 `tools/inspect_ipcm_tonal.py` 重新提取原厂ELF。证据在 [ipcm-tonal.json](../outputs/metol/ipcm-tonal.json) 和同名反汇编。

### 独立YLUT

| 位置 | 已确认内容 |
|---|---|
| UDD `ipcm_ylut`，`0x4b344` | 复制256个uint8到context+0x500 |
| IQ `CIpcmYLutD4::SetParam`，`0x340914` | 包含静态及自适应Y Gamma分支 |
| IQ `0x340a14` | 向UDD提交YLUT |
| 取景列表 `0x3407bc`／`0x3407c8` | 构造并加入YLUT节点 |

这证明原厂有独立亮度表参数链，没有证明它在所有模式下启用，也没有证明它位于当前Tone之前或之后。本轮没有新增YLUT挂钩或改变开关。

## 统一算法

`tools/ipcm_preview_tonal.py` 对所有风格使用同样的设置，不接收风格名：

1. 合成训练样本按60% RGB体积、20%灰阶、20%近灰分配权重；照片不参与拟合。
2. 联合目标包含RGB、OKLab和有符号灰阶色度。近灰权重只取决于输入；保留源LUT自己的冷暖，不把有意染色强制变中性。
3. 先优化65结点Tone，再优化两个矩阵，最后联合微调；曲线保持单调并惩罚曲率，矩阵加入单位变换正则。
4. 25／50／75／100%共同求解。模型按真实参数强度混合求值，没有降低预览强度。
5. 在另一组样本上比较原生参数量化后的结果。各强度RGB体积均值不得超过基线加 `max(0.10码值, 2%)`，P95不得超过基线加 `max(0.20码值, 3%)`；在合格候选中选择共同目标较低者。

这是一轮有约束的局部优化。保存了各阶段连续参数和量化结果，没有证明全局最优，也没有据此宣称整个IPCM能力已用尽。

运行时仍只加载预编译缓存，磁盘格式兼容现有v1／v2。本轮未修改RAM代码、IPCS 9³成片、196字节配置、RAW或安装包。

## 全库评估

同一训练／选择协议用于20款。最终测试使用seed=73091的24,000个独立RGB点、1,024级灰阶及两张未参与训练的NX照片。8款使用保存的预览配置作为旧基线，其余12款本轮首次建立原算法基线。

完整数据报告RGB均值／P95／RMSE、OKLab距离、明度、明度P10–P90跨度比、色度、HSV饱和度和色相角；另按近灰、绿色、蓝色、肤色类似码值区域及暗中亮区统计。区域是RGB阈值，不是场景语义分割；OKLab计算按sRGB假设，不是实机ΔE00。

以下5款选中了新候选，其余15款的参数保持基线：

| 风格 | RGB均值旧 → 新 | 灰阶色度旧 → 新 | 结果 |
|---|---:|---:|---|
| GR Neg | 8.757 → 8.756 | 2.004 → 1.556 | 灰阶改善，50%肤色类似区域RGB误差增加0.270 |
| Portra 400 | 0.810 → 0.568 | 1.100 → 0.555 | 明显改善，50%绿色区域增加0.162 |
| Ektachrome E100 | 0.630 → 0.665 | 0.516 → 0.498 | 灰阶小幅改善，整体RGB和感知均值略退步 |
| Superia 400 | 0.498 → 0.507 | 0.785 → 0.771 | 小幅取舍 |
| Velvia 50 | 0.988 → 0.917 | 0.726 → 0.757 | RGB改善，灰阶及感知均值略退步 |

上述选择依据四档强度的共同目标，不能解读为每一项指标均提升。完整表格列出20款和所有检查区域的最大退步；没有将这5款自动替换默认配置。

## NC为什么仍不对

NC源LUT灰阶在暗部偏冷、亮部偏暖，当前模型暗部常向相反方向偏。100%下：

| 输入灰阶 | 源LUT目标RGB | 当前模型RGB |
|---:|---|---|
| 64 | 51.62, 56.93, 56.38 | 58.71, 56.53, 54.52 |
| 96 | 88.74, 92.06, 92.20 | 97.35, 93.12, 88.76 |
| 160 | 190.50, 178.30, 174.41 | 188.56, 181.76, 175.64 |

暗部有效R−G／B−G分量中65.35%方向相反；只统计源目标偏色至少1码值的分量，分母456。全RGB均值4.414、P95 10.707；平均色相偏差3.12°、P95 8.50°。这些平均值不会显露全部灰阶错向。

选中连续解RGB均值4.425，参数量化带来的输出差仅0.186码值。新连续候选虽然降低共同感知目标，RGB均值变成4.627、P95变成11.830；量化候选没有通过共同退步限额，最终保留旧配置。量化不是这组模型中NC的主要问题。

同一配置套入码值／sRGB／原厂静态Gamma结点假设后，RGB均值分别为4.414／7.958／9.677。这是模型敏感性，不是三次机身测量，更不能根据哪个数字最小来认定真实Gamma。

## 三维表表示能力参考

为区分三维映射和参数拟合的限制，另对20款统一生成5³／7³／9³、10-bit节点表并进行软件三线性插值。没有写入原IPCS表。

NC在同一RGB测试集上的结果：

| 表达方式 | RGB均值 | 灰阶色度误差 | 灰阶有效分量反向比例 |
|---|---:|---:|---:|
| 当前IPCM参数模型 | 4.414 | 3.087 | 25.0% |
| 5³三维表 | 3.295 | 0.693 | 0% |
| 7³三维表 | 1.750 | 0.268 | 0% |
| 9³三维表 | 1.023 | 0.238 | 0% |

这些数值支持调查完整三维预览，并不代表纯CPU后端已在机身达到可用帧率。9³也不保证每款都比参数模型准确：例如Ektachrome、Velvia 50的平滑曲线用现有参数模型表达反而更准确。

## 验证与下一步

直接包含现有 `runtime/ipcm_preview_blob.c` 编译检查参数运算：303组矩阵、77,568项Tone强度结果与Python一致。三种Gamma假设下的颜色链Jacobian方向差分最大误差低于6×10⁻¹⁰。结果在 [math/report.json](../outputs/deployment/ipcm-preview/evaluation/tonal/math/report.json)。Python编译及20款评测／渲染命令均退出0。

本轮没有修改运行时，因此没有重复之前的28轮ARM参数通路检查。模拟器不执行真实ISP像素运算；机身仍缺动态原厂参数、处理顺序、真实取景帧和JPEG匹配对照。

按用户最新方向，优先复用原厂SmartFilter的取帧、工作线程、缓冲区和完成回调，调查YCC→IPCS 3D LUT→YCC。已确认的实际调用和新增3D开关绑定见 [原厂SmartFilter调查](SMARTFILTER_LUT_PREVIEW.md)。纯CCM／Tone／YCC继续无边界增加迭代的收益已很有限；PCSE和YLUT只有取得机型级响应后才继续纳入统一拟合。若原厂IPCS路线不适用，再在相同帧入口评估统一软件3D LUT，届时测量真实帧率与拍摄响应。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
python -X utf8 tools/inspect_ipcm_tonal.py

```
